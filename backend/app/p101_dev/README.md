# P101-DEV-1 — offline industrial snapshot adapter

`adapter.py` has no database, ORM, HTTP, filesystem, clock or configuration access.
It neither loads data nor writes predictions. It does not change the historical
P101 profile or the existing DEV evaluation/preparation contracts.

The caller supplies three immutable projections:

- `IndustrialChain`: companies.id, sites.id/company_id,
  equipments.id/site_id, sensors.id/equipment_id/sensor_type/unit.
- `IndustrialMeasurement`: measurements.id/sensor_id/timestamp/value/quality.
- `IndustrialSnapshot`: the chain, one explicit target, a tuple containing every
  candidate reference, explicit event cutoff/observation times and an existing
  `DeclaredProvenance` record.

Primary and parent keys must be native positive 32-bit integers, never booleans
or strings. Each parent FK is checked; each measurement must belong to the
resolved sensor. Unit comes from that sensor because measurements has no unit
column. Dates must be aware native datetimes. UTC normalization preserves the
instant and microseconds; naive dates are rejected, never assigned a timezone.

The projections are a future injection boundary, not proof of actual SQL reads.
A future trusted loader must authenticate/authorize the requested company,
resolve the industrial chain and read all relevant candidates in a coherent
snapshot. Do not pass live ORM objects/relationships that can lazy-load here.
The existing paginated measurement repository, especially with a quality filter,
does not itself prove a complete evaluation window. Candidate omission upstream
cannot be discovered by this pure adapter. No SQL loader is installed in this lot.

No selection, quality filtering, truncation, date repair, interpolation or gap
filling occurs. More than 32 references is a structural rejection; otherwise
all supplied references reach existing preparation. It sorts them chronologically
and requires exactly ten daily references before the target, temperature in °C,
good quality, finite values, no duplicate IDs/times and a coherent time cutoff.
The existing engine alone computes reference mean/std, threshold and alert;
zero std and nonfinite statistics remain its explicit abstentions.

`adapt(snapshot)` returns normalized `EvaluationInput` only after the existing
engine confirms calculability; otherwise it returns its `Abstained` or `Rejected`
outcome unchanged. It performs one engine evaluation on structurally valid input.
If the computed result is needed directly, use `evaluate_snapshot(snapshot)`:
it adapts and evaluates once and preserves `Computed | Abstained | Rejected`.
Calling `evaluate(adapt(snapshot))` would compute twice for a calculable snapshot
and requires first checking that adaptation returned an EvaluationInput.

Provenance is mandatory and explicitly supplied: no default synthetic flag,
environment-derived source, invented historical availability or attestation.
Existing provenance validation is reused, including its allowed optional evidence;
declarations remain unauthenticated and confer no B2B permission. The result
continues to state that availability at the historical target time is not attested.

Synthetic example in `tests/p101_dev/test_adapter.py`: references
65, 63, 67, 64.5, 65.5, 64.5, 65.5, 65, 65, 65 °C, daily before a 70 °C target.
Mean is 65, sample std 1, threshold 3 and absolute deviation 5. The result has
score 1 and is_alert true. Score is a binary anomaly indicator, not a probability
of failure. No prediction ID, created_at or SQL row is generated by the adapter.

Targeted validation only:

```powershell
& backend/.venv/Scripts/python.exe -B -m pytest tests/p101_dev -q -p no:cacheprovider
```

Fixtures are constructed business projections; infrastructure imports and socket
connections are blocked using the existing pure-evaluation test fixture. These
tests prove no live DEV schema, data availability, authorization or persistence.
